# 第一轮排查指引与试用计划

日期：2026-10-17（Asia/Shanghai）。版本：draft-1。方向以 [product-direction.md](product-direction.md) 为准。

前三节可独立用于阅读已有记录和填写交接材料，不需要 AI。第四节为后续试用计划。本轮只完成来源核对和文档编写，没有执行采集、检查、缺陷重建或用户试用。

## 1. 开始：只带已有记录

适用对象：本摄像头项目的 Windows 用户。先选定一次问题与记录目录；不要凭“最近那个文件”拼接不同运行。记下项目版本、发生时间、工具名称和参数；不知道就写未知。

1. 从下表选择场景卡。不属于这些情况或无法理解记录，保留原始错误并直接交接。
2. 用第三节模板记录观察、来源与缺口。结果文件用文本查看，不执行里面的命令，不打开 QR 链接。
3. 按卡片先核对已有材料。需要补充实测时写“待用户手动操作”，助手不执行；本轮试用首先使用历史结果回放。
4. 用户另行操作后，把新结果追加为证据，注明时间、操作、版本与条件差异，保留旧失败。没有可比结果就保持“待结果/不可比较”。

| 你遇到的情况 | 场景卡 | 首先准备 |
| --- | --- | --- |
| QR 有读出、歧义或 ROI 结果不同 | G1 | 已有整图/ROI 分析记录、图片标识、独立答案是否存在 |
| 任务完成，但复核提示图片或指标问题 | G2 | 任务记录、已有复核输出、对应 CSV/图片位置记录 |
| 设备打开失败，之后似乎恢复 | G3 | 失败运行记录、后续运行及复核记录、用户操作说明 |

只分享本次问题所需的材料。交接前检查个人信息、本机路径、图片与 QR 载荷；未经允许不附原图或载荷。脱敏时保留本地原件与替换说明，不能删掉关键证据后仍声称结论充分。

## 2. 场景卡

### G1：QR 读出了，是否代表正确？

**适用**：已有 QR 分析结果。普通说明：程序是否完成、是否读出、是否与正确答案相同，是三件不同的事。

**下一项检查**：在 `label_baseline` 报告中，先看顶层 `status`，再按 `decode_summaries` 内的 `region` 找到整图/ROI 对应项，分别读取该项的 `decode.status` 和 `truth_check.status`。原始尝试留在 `attempts`；即使汇总可读，也保留其中的失败和 warnings。整图与 ROI 用同一图片标识配对，记下 ROI 范围，不能只挑较好的一次。只有验收汇总文件时，先读其 `decode_status`/`roi_status`、`truth_status`，再沿 `result_file` 定位原报告；原报告缺失就登记缺口。

| 看到的结果 | 可以写什么 | 还缺什么/下一步 |
| --- | --- | --- |
| `decoded` 且真值 `not_provided` | 单一读出，内容正确性未验证 | 询问是否有独立原始载荷答案；没有就保持未验证，不能把解码结果反填为答案 |
| `ambiguous` | 存在歧义，尚不能选定有效答案 | 保留状态及整图/ROI 对照，交接技术人员；不认定现场一定有多个二维码 |
| 解码为 `decode_error`/`execution_error`，或整体为 `completed_with_errors` | 分析包含解码或执行错误 | 保留原始错误类型、工具参数与退出码；根因未知，不能改记成功 |
| 有独立答案且结果为 `correct` / `incorrect` | 报告记录了逐字节比对结果 | 核对答案独立来源、图片身份与比对范围；不扩展成整机或跨场景合格结论 |

**带回/保留**：结果位置、图片标识/已有摘要、整体与解码状态、真值来源/状态、整图或 ROI 参数、工具版本和退出码（没有原始退出记录就写未知）。用户另行分析时保存新结果，不覆盖旧报告。

**复验/停止**：先明确目标是“可读”还是“内容正确”。前者改善不能代替后者；没有独立答案就停止正确性判断。ROI 不保证改善；重复读出一致也不提供独立真值。需要新分析且用户尚未手动执行时，停在待结果。

**依据 E1**：既有 18 张实拍整图记录为 14 单一读出、4 歧义；ROI 为 14 单一读出、3 歧义、1 解码错误，均无独立答案。这是历史记录核对，不是本轮执行，也不是正确率或 18 个独立场景。

### G2：任务完成，为什么还有缺图或指标不一致？

**适用**：已有 `capture_task_review` 输出。普通说明：采集记录写着完成，不代表每份图片和数据都能核对；核对发现不一致，也不一定是复核程序崩溃。

**下一项检查**：先记下 `task_status`，再看 `verification_status` 和 `issues`。定位到同一 `run_id`、`frame_count`，分别抄录 `reported_samples`、`csv_pairs`、`verified_frames`，不能互相替代。

| 已有复核结果 | 解释 | 下一项人工核对 |
| --- | --- | --- |
| `consistent` | 本次检查范围内记录一致 | 核对范围、帧数和 warnings；不能写相机合格 |
| `frame_unverifiable` | 对应帧无法核实 | 看 detail 是缺失、不可读还是其他问题；核对图片位置、是否拿错/漏带目录。该代码本身不能证明磁盘写入失败 |
| `metric_mismatch` | 记录值与复算值不同 | 保留指标的两个值、摘要匹配状态和 comparison_basis；核对批次与算法上下文，不直接归因为相机损坏 |
| `not_reviewed` 或输入解析错误 | 没有完成有效复核 | 保留 stderr/错误记录与任务状态；先补齐可读输入，不判断数据一致或不一致 |

**带回/保留**：任务与复核结果位置、工具/版本、原始退出码、问题帧号、issues/warnings 原文、CSV/图片标识、缺失项、用户实际做过的动作。先读现有输出，不要求普通用户重新算指标。

**复验/停止**：用户在外部另行核对后导入新结果。仅在同一问题对象、材料/版本变化有说明、相关检查完成且目标问题不再出现时，记录“该范围复验通过”。另一批正常数据不能证明旧批次缺图已恢复。无法确认关联就交接，不编辑 CSV 来匹配结果，不覆盖原图或旧记录。

**依据 E2**：已有合成缺图反例为 `task_status=completed`、`verification_status=inconsistent`、`verified_frames=0`；指标反例为亮度 `101.0` 对 `100.0` 且图片摘要匹配。正常合成例为 `consistent`、三个数量均为 1。它们是不同 fixture/run_id，不能把正常例当作两个反例的恢复证明。历史审计记录将两个反例退出码核对为 1，当前复核源码也区分 0/1/2；本轮仅静态与记录核对。

### G3：设备打开失败后，如何判断恢复？

**适用**：已有 `failed/open_failed` 记录及可能的后续采集结果。普通说明：这表示该次打开没有成功；单凭它还不能确定编号、占用、权限、驱动或硬件原因。

**下一项检查**：对照失败记录的请求编号/后端与用户原本想使用的设备。再查用户已手动重试产生的新记录，核对时间、编号、采集状态、实际帧数和复核结果。没有新结果就写“待用户手动操作/待导入”，不自动打开设备，也不默认建议重装驱动或更改权限。

**带回/保留**：失败记录、stderr、请求编号/后端、用户实际改变了什么、新运行 ID/时间/参数、已有采集与复核结果。“预览正常”的描述单独存为用户反馈，不能替代记录。

**复验/停止**：若后续目标设备采集完成并有相匹配的有效复核，只写“该设备在这些条件下重新采集与复核成功”。条件改变须明示；不能确定原失败根因，不能宣称物理拔插、断连恢复或驱动故障已验证。再次失败或资料不足就交接，不无限建议重试。

**依据 E3**：已有不存在编号 9999 的记录为 exit 2、`failed/open_failed`，其复核 exit 2；后续实际设备 0 的恢复预览复核为 `consistent`、2 帧。它支持该组历史操作，未验证物理拔插和中途断连。本轮未启动摄像头。

## 3. 共用调查与交接模板

这是手工填写模板，不是已实现的数据格式或导出功能。复制到本地新文档保存，空白项写未知；新结果追加，不覆盖旧条目。普通说明与技术详情使用相同调查 ID 和证据 ID。

| 字段 | 填写内容 |
| --- | --- |
| 调查身份 | 调查 ID、日期/时区、场景/步骤 ID、指引版本、项目版本 |
| 用户目标与现象 | 想完成什么、发生什么、反馈原话与时间 |
| 执行情况 | 每次操作的执行者、时间、工具/版本/参数、阶段、状态、退出码及来源；助手本次执行检查=未执行 |
| 业务问题 | 观察及对应证据 ID；不由退出码直接推断业务成败 |
| 证据索引 | E01…；文件位置、JSON 字段/日志行、原始或副本、已有摘要及来源；缺失/截断/未核验摘要显式记录 |
| 下一项人工动作 | 目的、步骤 ID、输入、应带回材料、停止条件；建议/用户报告已做/已收到结果分别记录 |
| 用户反馈 | 操作后主观是否改善、说明与时间；与执行记录分栏 |
| 复验 | 目标、前后证据 ID、对象/条件/版本是否可比、通过/未通过/不可比较/待结果及理由 |
| 根因判断 | 未知或候选；支持、反证与缺口；原因未确认也可正常交接 |
| 交接 | 简明结论、尚未验证、下一项建议、可分享附件及删改说明、交接原因 |

交接前核对：接手者能定位关键观察；能区分“没做”“做了失败”“用户说好”“已有复验支持”；缺失项未被补猜；附件与结论属于同一次运行或明确列出差异。同一记录可呈现短说明与技术详情，不能各自维护事实。本轮不联系或发送给技术人员。

## 4. 第一轮试用计划（尚未执行）

**顺序**：作者先做资料回放走读，检查入口与模板，标为作者自评，不算外部验证。之后计划邀请 3 名有该项目使用需求的 Windows 用户自助阅读，另请 1 名技术接手者只看交接文档。本轮未招募或联系任何人。

**材料准备**：采用 E1–E3 的既有结果，经人工审查制作最小脱敏副本，登记来源、版本、摘要、删改与缺失项。源文件原字节保留，原图/真实载荷默认不分享。不能假定其他用户拥有私有忽略目录；试用前须确认副本可打开且脱敏未破坏关键字段。本轮尚未制作分享包。

**三项任务**：G1 解释单一读出但无答案，以及 ROI 出错；G2 解释已完成任务中的缺图/指标差异并指出下一项核对；G3 根据失败与恢复记录判断支持什么、还不知道什么。只给问题和材料，不提前给期望结论。

**回放方式**：用户先解释现有记录并写下一步；需要新结果时，主持者提供预先审查的历史后续记录，明确标为回放。G3 可回放真实历史前后关系；G2 正常 fixture 是“不能证明旧问题恢复”的反例。回放只能检验指引理解与交接能力，不能证明现场修复能力。新采集/复测须未来另行安排和授权。

**对照**：A 使用原项目现有说明与记录，B 使用相同范围材料加本指引/模板；均无需 AI，均允许停在证据不足。参与者交错 A/B 顺序，使用不同但难度相近的题目；无法避免重复材料就记录学习效应，不声称因果改善。同一作者的结果不能充当外部采用证据。

| 指标 | 记录方法 |
| --- | --- |
| 结果正确性 | 按五个维度核对，重点看是否把读出当正确、缺图当磁盘故障、反馈当复验、恢复当根因 |
| 下一步可执行性 | 能否指出一项有目的、输入/返回材料和停止条件的人工动作；找不到则记录卡点 |
| 自助成本 | 从打开材料到交接的时间、找文件次数、求助次数、放弃原因；准备/脱敏成本另记 |
| 交接质量 | 接手者能否不问作者就定位关键证据、说明未知和下一步；补问数量及内容 |
| 再用意愿 | 什么真实任务愿意再用；有实际再用才记采用，口头意愿不是留存 |

**预先约定门槛**：关键误判必须为 0；出现任一关键误判，先修正文案并针对该误判重试，不进入向导。初轮 3 人中至少 2 人无需作者解释完成全部三项任务和一份可接手记录，才支持继续探索；缺额则报告样本不足。接手者须能定位关键证据。小样本不能外推准确率或市场需求。

**向导触发条件**：质量门槛满足后，至少 2 人出现相同的找文件、漏步骤或整理困难，且简化文档仍不能解决，才考虑对应的最小交互。若 A 已同样容易、B 增加负担或无重复需求，就缩短指引，不加程序。API/动态取证另需无 AI、固定证据解释、受限动态取证和最终证据回放的对照，不在这轮推进。

试用记录至少含匿名参与者 ID、角色、任务/材料/指引版本、A/B 顺序、完成/未完成、用时、求助/误判、反馈、接手结果与修订决定。不预填成功率、节省时间或模型收益。
