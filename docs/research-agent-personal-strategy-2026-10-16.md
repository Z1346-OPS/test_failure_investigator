## 1. 核心结论

个人有机会做出有用的 Agent 辅助工具，但应从反复出现的具体工作开始：整理失败材料、检查验收缺口、核对数据契约、形成可交接的调查记录。先证明其中一项的实际效用，再决定是否需要模型自主选择工具。

当前没有证据证明原“测试失败调查 Agent”在准确率、速度或费用上优于直接使用现有编码助手。安全边界、轨迹和状态分离是可靠工程的基础；只有它们降低了目标用户的核验、返工或接入成本，才构成用户购买或持续使用的理由。

对当前项目最合理的下一步是：**先选择一个真实高频痛点，做一次现成工具/提示词/最小程序的对照。** 优先验证“pytest 任务定向证据整理”；如果实际困难是助手完成后仍需反复追问验收，则优先验证“变更验收辅助”。暂不同时建设两套产品，也不承诺“更强通用 Agent”。

需要分开三种成功：

| 目标 | 成功的证据 | 不能拿来替代的东西 |
| --- | --- | --- |
| 学会 Agent 工程 | 工具边界、状态、记录和反例可解释、可验证 | 框架数量、代码量、漂亮演示 |
| 对自己有用 | 真实任务反复使用后，节约的工作超过配置与维护 | 自己已经知道答案的单个案例 |
| 对别人有吸引力 | 别人能低成本完成任务、无需作者陪同，并愿意再次使用 | 点赞、一次试用、面试时讲得完整 |

以下方案均为待验证的产品假设，不是已经发现的市场空白。

## 2. 这几轮讨论形成了什么，哪些观点需要修正

### 2.1 已形成的方向

1. 起点是独立的本地 pytest 失败调查工具。模型选择调查与解释；程序控制读取、预算、证据及状态。摄像头工程只是第一个接入对象。
2. 随后提出产品质疑：既然现有编码助手可以读取项目，为什么再安装一个调查工具？因此必须与直接使用助手比较。
3. 对上下文准备提出假设：在模型前整理数据，可能减少人工挑选和无关输入；但摘要生成、后续补读与多轮对话也可能增加总成本。
4. GitHub 调研显示，上下文打包、符号检索、工作流、Agent 执行系统已经有实质项目。自研需说明比现成组合多解决哪项工作。
5. Anthropic 审查实践引出了另一种候选需求：在代码已生成之后，把“做了什么、验证了什么、哪些仍未知”变得易核对。

这些是选择依据，不是原产品已经失败，也不是新产品已经成立。

### 2.2 不能继续沿用的绝对判断

| 前几轮出现的说法 | 本报告的修正 |
| --- | --- |
| 通用编码助手是黑盒，用户不知道读了什么 | 不应笼统概括。不同宿主、模式和配置的可见性不同；本轮没有做其逐项产品审计 |
| 个人用户不在乎核验，只在乎快 | 未经用户研究。个人可能在发布、交接、长期维护时重视核验，也可能认为额外记录麻烦 |
| 作为排错工具一定打不过现有产品 | 尚无对照。通用任务竞争激烈，窄任务仍需实测，不能提前宣布胜负 |
| 裸模型或单次模型必然深度不够 | 充分材料下可能已经足够；应是有效基线 |
| 差不多快、差不多准就没有产品价值 | 还要比较准备负担、使用频率、接入、费用和可交接性；相近质量可能有便利性价值 |
| 安全限制一定是卖点／一定不是卖点 | 看具体用户与任务；边界可降低顾虑，也可能增加配置成本 |
| LogDx-CI 直接验证了我们的产品假设 | 它提供特定日志任务的研究支持，不能外推到本地源码调查或本项目收益 |
| MLflow analyze-ci 本质是单次模型调用 | 其 skill 要调用脚本、读取失败日志；文件没有固定模型调用次数，不能如此归类 |
| 输入短了就省 API | 必须统计预处理、所有补读、重试和输出；调用数、token 数与费用是不同指标 |

这些修正避免把讨论中的推断包装为事实，也避免为了保住一个项目而修改评价标准。

六类七仓库的深度抽查与两项补充样本的力度不同，不能合成“九个仓库全部审查达标”。研究论文、团队经验和源码质量也不能使用同一评分标准。

### 3.2 工程质量如何判

| 检查维度 | 可接受证据 | 常见误判 |
| --- | --- | --- |
| 来源与许可 | 官方 owner、组件 LICENSE、固定版本 | 只看仓库名或旧印象 |
| 实质实现 | 入口、核心数据流与异常路径 | README 功能列表当实现证明 |
| 行为测试 | 断言输出、反例与真实文件系统行为 | 有 tests 目录就算覆盖充分 |
| CI | 工作流命令、对应 SHA、job/step 状态 | 绿色徽章证明本机可用、安全、无跳过 |
| 维护 | 默认分支时间、明确声明、版本关系 | 定时机器人活动等于源码维护 |
| 权限与依赖 | 配置执行、命令、网络、写入和隔离 | read-only、Plan、MCP 或 Docker 名称等于安全 |
| 用户效用 | 同任务比较，含准备与后续返工 | token 更少、报告更长或 Agent 更多等于更有用 |

“工程参考达标”只表示值得阅读和进入进一步评估；“可安装”“本机可用”“效果更好”需要另行验证。本轮没有项目获得后面三个结论。

### 4.2 Repomix：优先作为上下文准备基线

固定版本 [pack 流程](https://github.com/yamadashy/repomix/blob/55c6de6aebde4c38877fbcaf005c4cc396bf6e2d/src/core/packager.ts)及[预算行为测试](https://github.com/yamadashy/repomix/blob/55c6de6aebde4c38877fbcaf005c4cc396bf6e2d/tests/cli/actions/defaultAction.tokenBudget.test.ts)有实质实现；[对应 CI](https://github.com/yamadashy/repomix/actions/runs/38153526263)查询时成功。

值得借鉴的是把选择、处理、输出和预算分开。需要保留的限制是：[TS/JS 配置加载](https://github.com/yamadashy/repomix/blob/55c6de6aebde4c38877fbcaf005c4cc396bf6e2d/src/config/configLoad.ts)会执行代码；预算超限仍可生成输出，调用方必须检查非零结果；[真实符号链接测试](https://github.com/yamadashy/repomix/blob/55c6de6aebde4c38877fbcaf005c4cc396bf6e2d/tests/core/file/fileSearchConfineSymlink.test.ts)在 Windows 直接返回，没有执行该反例断言。

**判断：** 先比较人工选文件加现成打包工具与直接使用助手。自研仅剩“从特定任务自动挑必要材料、保持原行号与缺口”的窄机会，不能重复做通用整仓打包并称为创新。

## 5. 早期三个参照的补充核实

### 5.1 ai-test-failure-analyzer：固定编排属实，宣传准确性尚无证明

本轮固定提交 08d6a659ebbba1ebdeff971adad3cc9359a722c3（2026-07-24），读取了 [README](https://github.com/aks-builds/ai-test-failure-analyzer/blob/08d6a659ebbba1ebdeff971adad3cc9359a722c3/README.md)、[编排](https://github.com/aks-builds/ai-test-failure-analyzer/blob/08d6a659ebbba1ebdeff971adad3cc9359a722c3/analyzer/orchestrator.py)和[假设形成代码](https://github.com/aks-builds/ai-test-failure-analyzer/blob/08d6a659ebbba1ebdeff971adad3cc9359a722c3/analyzer/hypothesis.py)。

已核实：主编排安排收集、关联、假设与报告；README 声称 24 类解析器，仓库描述说 8 阶段，而正文/编排使用 10-phase 等口径。本轮未逐个验证 24 类格式、测试、CI、安全或安装链，因此**不授予与第 4 节同等的工程达标结论，也不据支持数量断言成熟度**。

值得警惕：假设代码含按 HTTP 状态形成标题的启发式，以及旧兼容路径按来源数量给分；v2 可委派图评分，本轮未完整审计。它们均不能仅因被叫作 confidence 就当成校准后的概率。单一 404、缺文件或名称相似都不足以确认数据迁移、磁盘写入失败等具体根因。不能把这段抽查扩大为所有新路径都只按来源计数。

**可借鉴：** 解析与证据收集分层、固定流程作为基线、保留原始定位。**不能照搬：** “有 file:line 就证明根因”“有来源就给高百分比”“夹具永远不可能是根因”等绝对口径。

### 5.2 MLflow analyze-ci：小技能可以有实用范围，但不能叫固定单次模型

本轮固定提交 96a768019f5aea1abac3406d1c884b04fbbe649b（2026-10-16），读取 [.claude/skills/analyze-ci/SKILL.md](https://github.com/mlflow/mlflow/blob/96a768019f5aea1abac3406d1c884b04fbbe649b/.claude/skills/analyze-ci/SKILL.md)。

它规定：输入 job/run/PR URL，调用 fetch-logs 命令，读取失败步骤日志，输出逐 job 摘要，并保留原始日志、步骤日志及可选包版本路径，供后续深入读取。没有输入则停止。它没有固定底层推理次数，也不禁止宿主继续调查，因而不能拿它证明“单次模型路线”。

**价值：** 窄入口、确定性脚本负责收集、模型解释、输出可继续读取的路径，这是一种可借鉴组合。**未知：** 本轮未审计 fetch-logs 脚本闭包、测试、凭据与网络实现；MLflow 整仓声誉不能替代这个 skill 的行为验证。未安装或执行该 skill，也未授权它发送信息或修改项目。

### 5.3 LogDx-CI：支持做实验，不能代替我们的实验

[技术报告](https://arxiv.org/abs/2605.28876)描述 35 个真实 GitHub Actions 失败案例，比较多种日志缩减及单次/工具循环诊断。在作者特定实验中，方法间分数范围从 0.42 收窄到 0.059；这说明补充读取可补偿部分初始材料缺失，不说明所有源码诊断都提高，也不是本项目准确率。

更正早期转述：“4.5 倍少 token”的摘要参照是 standalone grep，不是“全量日志且同等准确”。作者[结果页](https://logdx-bench.github.io/leaderboard.html)还说明，部分费用按字节估算及固定价格，Agent 实验的模型和预算有限；LLM 预摘要自身成本可能压过下游省下的用量。网页混列不同版本，排名不得脱离版本引用。

**判断：** 值得借鉴其端到端计费和补证据对照；没有独立复现或同行评审核实，本轮不以研究数字为营销承诺。

## 6. Anthropic 审查文章：能借鉴什么

资料为 2026-10-15 [官方原文](https://claude.dev/blog/solving-code-review-at-anthropic/)；用户最初提供的是 [AIHOT 译文](https://aihot.news/items/x02vc0ewajam37hjrbpwsfnre)。本轮以官方原文和产品文档核实。

### 6.1 事实、证据强度与边界

团队自述 6—9 月合并 PR 超过翻倍、回退比例下降超过 40%，并介绍分层检查、风险分级、事故评测与快速回滚。它也报告过五十多轮审查修复循环，随后限制轮数、去重、缩小复审范围。

这是有操作细节的团队经验。多个机制同时变化，缺少足以独立归因的公开对照；不能把收益归于某个 Agent，也不能外推到个人周末项目。

[公开 Code Review 文档](https://code.claude.com/docs/en/code-review)说明，服务阅读 diff 与周边代码，不构建或运行工程；它发布发现但不批准或阻断 PR。文章中的执行验证和合并门禁是更大流程的一部分。产品没有发现也不证明没有缺陷。审查指令来自基线分支而非待审 PR，这一点可借鉴到可信规则来源。

### 6.2 对个人可缩减的实践

| 参考思路 | 最小采用方式 | 需要检验的代价 |
| --- | --- | --- |
| 显示验证输出 | 记录来源、代码版本、执行状态与证据 | 记录是否比原工作方式更费时 |
| 短项目规则 | 保存真正重要的契约与验收项，按需加载 | 过期、冗长规则可能误导或浪费上下文 |
| 新上下文审查 | 只交付任务、代码和证据，不继承实现者自评 | 同模型仍可能共享偏差，需客观检查 |
| 审查收敛 | 去重、限制轮次，无新增证据时停止 | 停止不代表已穷尽问题 |
| 事故形成评测 | 加入正常、失败与未完成案例 | 开发集反复调参会污染结论 |
| 将人工时间与返工一起计量 | 同时看准备、阅读、追问与后续修复 | 很短的观察期看不到发布回归 |

本表是本报告的适配建议。个人无需先复制多 Agent 投票、自动合并、值班、发布渠道和完整平台。多个模型同意也不是执行验证。

## 7. 原失败调查项目还保留什么价值

### 7.1 保留的工程基础

只读工具、真实路径白名单、参数校验、预算、证据存储、状态分离和答案隔离仍然有用。它们可服务于窄产品，也可作为学习与评测框架。它们本身没有证明商业需求。

先保留三个假设：任务定向准备能否省人工；按需补证据能否优于固定材料；独立状态记录能否减少无效核验。分别测，不合成一句“Agent 更好”。

### 7.2 摄像头开发案例的地位

以下继承[设计 v0](D:/AIProjects/projects/test_failure_investigator/docs/design-v0.md)的只读核实，本轮未访问摄像头源码或复跑：

- 正确契约是 reported_samples 保留任务 JSON 中 counts.samples_completed 的声明数。两个目标参数分支属于同一缺陷族。
- 当前可见源码已经正确；本地已检查的首次提交 66b05d6 也正确。只说明该可见历史未找到可直接检出的失败版，不说明其他地方不存在。
- 历史记录的 3 failed、9 passed 含另一个 CSV 异常缺陷；历史修复后的 12 passed 不是本轮测试结果。
- 受控重建计划只在独立副本把两处传值从 declared_count 改为 len(samples)。验收是两个目标因指定计数断言稳定失败、恢复正确实现后通过；不追求历史失败总数，不回退 CSV 缺陷。
- 初始调查可先限定失败版 review_capture.py、目标测试与必要 helper 的批准片段，以及失败/运行记录。测试执行闭包包含更多模块及 pytest、NumPy/OpenCV，不能因此全部开放给模型。
- 首例较容易从断言定位，适合验证工具边界和轨迹；若单次模型已经解决，不删契约制造 Agent 优势。

设计者的正确版本、修复总结、重建补丁、标答和私有记录必须隔离。尤其原任务文档已写出修复答案，不能通过搜索泄露。

### 7.3 技术设计与产品决策分开

原设计 v0 未作废，但没有新增实现授权。若后续确定新定位，再同步项目规则和设计。不要在本文提出五个方案后偷偷把项目扩成五个平台模块。

## 8. 个人如何构造 Agent：先选复杂度，再选工具

“用 Agent 帮我开发一个程序”和“程序内部必须运行 Agent”是两个决定。普通确定性工具也可以通过 Agent 辅助开发，并对用户有用；产品名称不必包含 Agent。

| 层级 | 适用条件 | 最小构造 | 升级理由 |
| --- | --- | --- | --- |
| 确定性脚本 | 解析、筛选、统计、格式化规则明确 | 输入校验 → 规则处理 → 可检查输出 | 需要语义解释而非继续堆规则 |
| 提示词/skill | 工作反复发生，但宿主已有文件和工具能力 | 短流程、输入要求、停止条件、输出模板 | 有稳定的重复数据操作或状态一致性问题 |
| 脚本加一次模型 | 证据能固定准备，主要需要解释 | 脚本生成材料 → 模型结构化解释 → 程序核验 | 固定准备经常遗漏，且补读有可测增益 |
| 受限动态 Agent | 下一步随证据变化，无法廉价固定枚举 | 显式状态机、少量读取工具、预算和终止 | 已有工具不足以完成已验证需求 |
| 执行/修改 Agent | 必须运行程序或改变外部状态 | 独立执行边界、命令契约、输出验证与回退 | 新阶段单独设计，不随读取工具默认加入 |

层级是工程选择，不是能力等级。个人优先把宿主已有能力用好；先不要自建模型路由、聊天 UI、插件市场、向量数据库或多 Agent 组织。

## 9. 最小可实施的通用构造

以下是未来方案共用的候选设计，未实现。

### 9.1 数据流与职责

用户任务和范围 → 输入规范化 → 任务相关材料选择 → 模型解释或申请补充 → 程序校验并读取 → 证据入库 → 有限循环或结束 → 程序状态加模型分析的报告。

| 模块 | 必须由程序承担 | 模型可以承担 |
| --- | --- | --- |
| 输入 | 格式、来源、大小、版本绑定与未知字段 | 识别需要澄清的语义 |
| 读取 | 正向白名单、真实路径、类型/字节/结果上限 | 选择允许材料中的下一项 |
| 记录 | 生成证据 ID、路径、行号、摘要及截断状态 | 解释引用支持什么、缺什么 |
| 预算 | 调用、总量、超时和重复请求控制 | 说明继续调查的预期价值 |
| 状态 | 读取失败、超限、模型不可用、执行来源与是否复测 | 候选原因、反证与建议 |
| 输出 | 校验 schema、引用与事实字段，保留不合规响应记录 | 写可理解的分析与未确认事项 |

引用存在只证明引用有效，不能证明支持结论。结构化输出不等于推理正确。

### 9.2 v0 权限和状态

先提供固定失败/运行记录读取、允许片段搜索和读取三类能力；不开放任意 shell、Git 修复历史、测试复跑、安装、写源码、自动提交或外部评论。

状态可为：input_invalid、collecting、awaiting_model、report_ready、partial、budget_exhausted、tool_error、model_unavailable。工具失败后是否继续由既定策略决定，不能靠模型把失败改成成功。

执行另设维度：not_executed、imported_record、completed、incomplete、unknown。导入历史测试不等于本次执行；pytest assertion failure、skip、collection error、timeout 与业务正常发现数据异常分别保存。不从缺文件推断磁盘写入失败。

每次新建 runs/<run-id>/，模型不能指定输出位置。代码版本可用 commit 加批准文件内容摘要；有未提交修改时不能只记录 HEAD。记录必要运行信息，不记录整个环境变量或活凭据。

### 9.3 最小技术与隔离

优先 Python 3.12、argparse/pathlib/json/hashlib、pytest；需要统一 schema 时采用 Pydantic 与其导出的 JSON Schema，不重复加入多个验证框架。真实模型阶段选一个官方 SDK，再核查具体工具调用、超时、数据保留与 usage 支持。

候选架构不依赖前端、MCP 或 LangGraph 才能成立。模型供应商、账户、版本、网络和实际计费正式接入前核实，不要求把密钥贴进对话。

初始证据、搜索和读取统一校验规范化真实路径，检测 symlink/junction/reparse 越界，限制类型/行区间/字节/结果/调用；读取结果标明截断。不执行仓库内不可信配置、skill、hook 或源码中的指令。可信项目规则来自人工批准版本，不从待调查材料自动获得指令权限。

读取服务的权限边界与宿主 Agent 的权限要分开。若宿主仍能直接读取整个仓库，服务白名单并没有隔离它；严谨评测需独立上下文和受限工作区。副本、.venv 和只读标签都不是 OS 沙箱。

## 10. 个人如何使用 Agent 帮自己开发

建议采用一个小闭环，避免“模型说完成”成为唯一验收：

1. **写清任务与完成条件。** 说明输入、预期行为、边界、允许修改与不可触及范围；让 Agent 先核实项目规则和相关代码。
2. **做一项可回滚的小改动。** 自己决定目标和范围，Agent 提出实现；不因生成代码便宜而自动扩功能。
3. **让确定性检查给证据。** 正式实现阶段使用已审查的测试/build/lint；记录命令、版本与结果。当前设计阶段无需伪造执行。
4. **对重要变更安排独立审查。** 给审查者任务、diff、必要周边和证据；不把实现者的自我证明当事实。不默认增加多个 Agent。
5. **亲自检查剩余风险。** 特别是路径、凭据、安装、CI 与数据写入；没有完整证据就保留未确认状态。
6. **积累失败，而非无限加规则。** 重复机械错误优先变成测试或 lint；语义约束写短规则；把真实回归加入隔离评测集。
7. **记录自己的操作负担。** 若每次都要解释同一件事、拼同一种材料、检查同一项缺口，那才是下一项自动化的候选。

推荐的一次任务说明应能回答：要解决哪个具体问题；涉及哪个工程和版本；有哪些允许读取/修改；什么输出可接受；如何验证；遇到缺证据何时停止。不要一次写几千字通用角色设定来替代这些信息。

## 11. 如何判断一个东西对别人有吸引力

### 11.1 把卖点写成可观察的工作变化

| 过早的宣传 | 可验证的价值假设 |
| --- | --- |
| 更聪明的测试 Agent | 从现有失败文件生成可直接交给助手的材料，减少手工挑选 |
| 更安全、更可追溯 | 分享前能看到选了什么、漏了什么；读入范围和未执行事项可核对 |
| 节省 80% token | 相同任务质量下，端到端实际费用与人工时间更低，比例测后再说 |
| 全自动完成验收 | 任务完成后列出尚无证据支持的验收项，减少遗漏与追问 |
| 多项目通用 | 在明确支持的格式和工程结构中接入负担较低；不支持时明确退出 |

使用理由可以来自质量、速度、费用、便利性、交接或垂直契约，不必所有指标同时领先；不能提升某一项却隐瞒另一项的恶化。

### 11.2 最小采用路径

从用户已有产物进入，例如现有 pytest 输出/JUnit XML、一次变更或一份任务 JSON/CSV；不要求先人工建立完整案例库。普通使用包与严格评测包应区分：后者的准备成本不能转嫁给每个普通用户。

先支持一种输入、一种语言或一种契约。输出简短 Markdown 与结构化记录，能由已有助手读取；配置常见范围可生成预览，用户审查后保存，避免每次逐行配白名单。默认拒绝不支持范围，别静默扫描所有工程。

首用、复用、维护成本分别统计。只有首次很顺、之后反复用、出错可理解，才可能形成吸引力。开源、插件形式或 Agent 标签不会自动解决这些问题。

### 11.3 从自己到其他人

先把自己真实使用的任务记录下来；若仅用一次，没有证据支持高频工具。之后可计划邀请 3—5 名同类开发者/测试工程师，在公开或明确授权的材料上自助试用；本轮不联系任何人。

观察他们能否独立完成、哪里退出、是否继续回到原助手，以及下一次是否主动再用。口头喜欢与实际复用分开记录；这仍是探索性反馈，不能外推市场规模或付费意愿。

## 12. 五个可能的方案

以下各方案都从一个窄任务开始；优先级是依据当前背景的判断，未有真实用户验证。不建议同时实现。

### 12.1 方案一：pytest 任务定向证据整理器

**谁用、何时用：** 个人 Python 开发者或测试工程师拿到一个失败输出，需要把相关材料交给现有助手，当前经常手工查找、复制、解释。

**一句使用理由：** “把一次 pytest 失败整理为可检查、可补读的最小材料，直接继续在现有助手中调查。”

**最小闭环：** 导入现有日志或 JUnit XML → 识别测试身份/阶段/断言 → 在批准工程范围定位测试、相关源码和 helper → 输出带原行号、来源及截断/缺失清单的证据包。不能从缺少记录直接认定某阶段成功；文本格式不支持时明确报告。

**Agent 的作用：** 首版可完全确定性，宿主负责分析；只有固定选择经常漏掉必要证据时，再允许模型通过 2—3 类只读工具补读。

**与现成工具比较：** 原助手直接分析、人工选择加 Repomix、短 skill 自动调用现有搜索。自己需要证明任务定向选择减少了操作或无关材料，且保留异常链、断言与参数。

**首版不做：** 自动运行 pytest、整仓上传、Git 修复历史、模型自修复、全框架、IDE UI。

**吸引力可能来自：** 少复制、少解释、可预览、同一包可交接；节省总费用尚未成立。

**指标与淘汰条件：** 准备时间、关键证据保留、后续补读、全过程用量与误归因。若原助手加一段提示词已经同样省事，或包准备更麻烦、经常漏证据，则不做独立产品。

**实现/维护判断：** 低至中；主要难点是解析不同 pytest 输出、参数化身份与动态 Python 调用关系，不承诺静态识别所有相关代码。

### 12.2 方案二：个人项目的变更验收辅助工具

**谁用、何时用：** 经常让助手改代码的人，完成后还要逐项追问“覆盖了哪些需求、测试的是哪个版本、哪些没检查”。

**一句使用理由：** “把任务要求与实际检查对齐，先告诉我哪些验收项还没有证据。”

**最小闭环：** 用户选定任务、当前变更和已有测试/构建记录 → 程序绑定版本与摘要 → 模型辅助映射需求、代码和证据 → 输出“已支持、存在缺口、无法判断”的短验收表。没有发现只能写未发现，不能写没有 bug。

**Agent 的作用：** 语义匹配和解释缺口；无需首版自主执行，也不必从头实现通用审查引擎。

**与现成工具比较：** 原助手加验收清单、Spec Kit 单流程、现成代码审查。只有跨记录的一致性、版本核对和缺口提示确实减少追问时才值得程序化。

**首版不做：** 自动合并、审批代签、自动运行项目命令、自动改正所有评论、承诺找全缺陷。

**关键边界：** 本方案本来就审当前变更，可以读取用户批准的 diff；原失败案例评测里的修复 diff 仍禁止。这两种任务不能共用一个宽松白名单。

**指标与淘汰条件：** 遗漏验收项、误报、误导修改、人工复核时间和返工。若它主要生成一份冗长“看似完整”的表，用户还得重新核对全部内容，则缩回短 skill。

**实现/维护判断：** 中；最大难点是接受“证据不足”，而非自动把所有需求勾为完成。

### 12.3 方案三：CI 失败分诊与交接助手

**谁用、何时用：** 多 job、多步骤 CI 失败，开发者要先弄清该读哪个日志、哪些失败可能属于同一问题，再交给自己或同伴。

**一句使用理由：** “先整理失败位置、关键错误和原始日志入口，减少在 CI 页面之间来回找。”

**最小闭环：** 首版只导入本地已下载 job/step 日志 → 规范化状态 → 保留错误前后文 → 形成逐 job 摘要及待查问题。远程 GitHub URL、认证和下载器以后单独加入。

**Agent 的作用：** 聚类候选与摘要，保留不确定性；确定性脚本负责日志边界、大小限制和来源。日志相似不自动认定同一根因，也不把 timeout 变成断言失败。

**与现成工具比较：** MLflow 类 skill、CI 原生失败摘要、固定 grep/tail 与宿主直接读取。市场拥挤，需要具体 CI 结构或特定团队任务才能形成增量。

**首版不做：** 自动复跑、创建 issue/发送评论、读取所有仓库、把环境变量或含秘密日志发给模型。

**指标与淘汰条件：** 找到正确 job/step 的时间、日志入口正确率、漏掉首个有效错误和误聚类。若单个 pytest 案例根本没有跨 job 负担，当前自己不需要此方向。

**实现/维护判断：** 中；后续接入远程 CI 会显著增加认证、服务兼容与数据处理成本。

### 12.4 方案四：JSON/CSV 与测试报告契约核对助手

**谁用、何时用：** 维护采集、数据处理或测试报告工程的人，要确认字段含义、计数、输入/输出对应和数据完整性是否符合业务契约。

**一句使用理由：** “把报告里的声明值、实际记录和可验证数据分开，指出违反了哪条契约及缺少什么证据。”

**最小闭环：** 人工确认的契约 schema 加批准的 JSON/CSV → 确定性检查声明数/实际数/缺失记录/状态 → 输出具体矛盾、正常的数据问题和未确认项 → 模型解释影响或建议下一项只读核查。

**Agent 的作用：** 解释多处矛盾、帮助提出下一步；计数和状态规则由代码判断。若纯规则已经足够，就发布普通检查工具。

**与现成工具比较：** 原有 review 工具、通用 schema 校验和现有助手直接阅读。必须找原工具未覆盖且真实重复出现的缺口；不能把摄像头已有复核功能重新包装为新项目。

**首版范围：** 先一种报告格式/一组计数契约，在独立新项目中只读接入，后续通过小适配器支持其他工程。reported_samples 案例只能作为开发例，不能代表需求规模。

**吸引力可能来自：** 可执行的垂直知识和稳定检查；相较通用上下文打包更有具体场景，但用户群可能更窄，需要本人持续遇到及外部同类用户验证。

**指标与淘汰条件：** 对契约违例的检出、正常数据误报、解释是否引导正确检查。若只有一个字段的规则，留在原工程就足够，不建立通用平台。

**实现/维护判断：** 小范围低至中，跨格式后中至高；契约必须版本化，不能让模型自行“纠正”正式字段含义。

### 12.5 方案五：Agent 取证与诊断评测台

**谁用、何时用：** 作者自己或研究工程师需要比较提示词、模型、材料选择和工具循环是否有增量。

**一句使用理由：** “把一次看起来成功的演示变成可以复查的对照结果。”

**最小闭环：** 冻结案例和标答 → 独立上下文运行固定流程/单次/动态/证据回放 → 保存状态与轨迹 → 人工核实诊断、证据和用量。

**Agent 的作用：** 被测对象；评测程序必须独立控制输入、标答隔离和预算，不能让被测模型决定自己是否通过。

**与现成工具比较：** 现有评测框架及 LogDx-CI 的组织方式；需要证明本地源码证据、状态或反例支持有必要。当前没有全面评测框架选型，不声称该需求无人覆盖。

**价值与限制：** 学习与研究价值直接，普通开发者的日常购买动机弱；适合公开方法与案例，不应伪装成面向所有人的排错产品。

**指标与淘汰条件：** 记录完整性、隔离反例、稳定评分与可复查。如果目标是赶快完成实际工程，而不是研究模型，不把评测平台做成无限前置工程。

**实现/维护判断：** 中至高；案例准备、有效标注和控制偏差通常比循环代码更费力。

### 12.6 如何取舍

| 方案 | 与当前背景匹配 | 首轮应证明 | 当前建议 |
| --- | --- | --- | --- |
| 任务证据整理 | 高，沿用原设计部分基础 | 比直接提问/人工打包更省准备，质量不下降 | 产品探索第一候选 |
| 变更验收辅助 | 较高，取决于实际追问频率 | 降低验收遗漏与人工核验 | 与第一候选二选一验证 |
| CI 分诊交接 | 条件性，有复杂 CI 才明显 | 找对失败 job/step 更省事 | 没有真实多 job 负担先暂缓 |
| 数据报告契约 | 有领域背景，但需求未验证 | 原工具没覆盖的重复契约问题 | 有高频痛点时可提升优先级 |
| 诊断评测台 | 学习/研究匹配高 | 比演示更能解释收益与失败 | 研究路线，非默认消费产品 |

“更有差异化”是待检验推断，尤其第 4 项没有做完整竞品扫描；不能说已经找到蓝海。

## 13. 如何证明速度、质量、成本与采用价值

### 13.1 产品比较与机制研究分开

**产品比较：**

- P0：用户正常直接使用现有助手。
- P1：同一助手加简短规则/skill 或验收清单。
- P2：同一助手加现成工具及人工选择。
- P3：同一助手加拟开发的最小工具。

固定工程版本、目标和可访问范围；记录模型/宿主、参数、时间及预算。宿主无法控制模型或内部提示时，将它标为真实使用比较，不把差异全部归因于某个组件。裸日志模型是辅助下界，不能作为唯一竞争对象。

**机制研究：**

| 路线 | 目的 | 不能证明 |
| --- | --- | --- |
| A：固定规则/固定取证 | 看程序规则或确定性准备是否已经够用 | 所有任务都不需要模型 |
| B：同初始材料单次模型 | 看动态补读相对起点是否有收益 | 相比正常读取工程的编码助手更好 |
| C：受限动态取证 | 看证据不足时能否有效选择补读 | 多轮推理本身更强，或白名单天然提高质量 |
| D：将 C 最终证据一次性交给模型 | 探索最终材料与多轮过程的贡献 | 严格分离两者的因果效果；证据已由 C 选择，有事后优势 |

D 应只回放工具生成的最终证据，不带 C 的分析、标答、修复答案。C 的选择成本另计，D 不可把这份材料视作免费。若使用不同提示长度、顺序或总预算，也须记录；C 与 D 的差异只是线索，还需重复与更严格控制。A 可拆为纯规则输出、固定证据加同模型，分别识别收集与解释的影响。

### 13.2 评价项

| 维度 | 记录内容 | 容易隐藏的成本或错误 |
| --- | --- | --- |
| 质量 | 正确候选、具体机制、关键反证、误归因、证据不足时的表现 | 位置对但原因错、靠已知答案猜对 |
| 证据 | 引用是否存在、是否支持该主张、是否漏必要上下文 | 有行号就当根因成立 |
| 时间 | 首次配置、准备、等待、人工阅读/追问、后续修复 | 只计模型响应 |
| 用量 | 预处理、全部请求、工具结果进入上下文、重试、输出与缓存口径 | 只计最后一轮或最终证据包大小 |
| 稳定性 | 相同起点多次运行、工具失败与超限、异常终止 | 只展示一次成功 |
| 采用 | 首次独立完成、再用、退出原因和支持请求 | 口头喜欢替代复用 |

实际费用按供应商可核对的 usage 与当时价格计；没有 usage/账单就写未知或清楚标注估计，不猜宿主内部成本。短输入可能增加补读和重试；一次调用也可能比多次更贵。

个人净时间收益可按“原流程总时间减新流程总时间，再减分摊的配置/维护时间”观察。分摊次数用实际复用次数，不用预计用户量稀释成本。时间与金钱分开报告，除非用户自行选择换算标准。

### 13.3 案例、偏差与停止

开发与留出按缺陷族分组；两个参数分支是同一族。加入正确实现、无关噪音、缺材料、读取失败、skip、collection error、timeout、提示注入和越界请求。

先做少量完整记录用于发现明显失败，不预填准确率目标。单个作者已知答案案例只能用于调试。后续冻结提示、工具、模型和评分规则后再看留出案例；评分最好由不了解路线的人复核，条件不足就标作者自评。

用户修了评论、点了赞或把线程关闭，不自动代表评论正确；要核对契约与行为。无问题案例必须纳入，防止工具“靠一直报错提高召回”。

预先写下继续/停止条件：关键证据被压掉、误报引导坏修改、准备负担上升、边界失守、成本不可测或没有重复需求时，先修正或缩回脚本/skill。没有收益不继续用更复杂架构解释失败。

## 14. 建议的周末与后续任务顺序

以下是未来计划，不是本轮已完成工作。周末目标仍以一个真实模型的只读取证轨迹为上限；时间不足停在可靠闸门。

| 顺序 | 工作 | 验收条件 | 未达成时 |
| --- | --- | --- | --- |
| 1 | 从自己真实工作中选一个痛点，记录当前流程 | 明确触发输入、产出、基线和重复负担 | 继续实际工程，不先写通用框架 |
| 2 | 若沿用摄像头案例，审查独立副本与执行闭包 | 两目标预期失败稳定；恢复通过；来源与原工程边界清楚 | 不接模型，不拿环境错误凑案例 |
| 3 | 冻结输入、私有标答和最小边界反例 | 模型可读与不可读清单；正常/缺材料/读取失败反例 | 缩小输入与工具 |
| 4 | 离线准备短提示/人工材料基线，记录人工成本 | 可对照起点已准备；模型路线留到后续正式比较 | 不宣称增量 |
| 5 | 建立离线证据整理、状态与报告闭环 | 无模型也能输出事实、缺口和真实错误 | 修工具，不伪造模型轨迹 |
| 6 | 按需求核查 SDK/API，完成一次真实只读模型轨迹 | 工具请求校验、证据引用、预算和未复测状态正确 | 保存失败，不接执行/自动修复 |
| 7（后续） | 正式多路线对照，决定保留程序、缩回 skill 或停止 | 质量、人工时间、用量、维护代价同表呈现 | 不为了项目完整而扩功能 |
| 后续 | 若本人重复使用，再做小规模外部自助试用 | 真实再用、退出原因与接入负担可记录 | 不急着前端、发布平台与商业化 |

若首选变更验收，则第 2 项改为准备真实任务、批准 diff 与匹配版本的已有检查记录，不需要先制造缺陷。不能为不同方案强行复用含答案的同一评测包。

## 15. 个人总结与选择建议

个人构造 Agent 的顺序应是：找实际反复工作 → 用好现有助手 → 固定输入和验收 → 把机械部分程序化 → 只在需要时加入模型解释与按需取证 → 保存失败并对照 → 反复使用后再做插件分发。

Agent 的价值可以来自拿到正确资料、把领域契约执行到位、减少交接与核验、避免重复操作。模型更强并不会自动消除输入混乱或事实记录问题，但这些问题也可能已经被现有工具解决。

对当前背景的明确建议：

- **想做一个自己先用、再让别人试的小工具：** 从方案一或方案二选一个；验证后再确认产品名称与接口。
- **经常面对报告数据含义错误：** 方案四可能更贴近自己的领域，先确认已有复核工具的缺口。
- **想学习 Agent 工程、做可解释的实验：** 保留方案五的最小评测能力，不把它宣传为日常排错产品。
- **暂时没有重复痛点：** 先使用现成工具完成实际工程，同样是合理选择；不需要为“做 Agent 项目”制造任务。

这是一组有顺序的候选，而非同时开工清单。对他人的吸引力最终由“无需作者陪同也能省下一项真实工作，并愿意再次使用”检验。

### 16.2 风险与回退

| 风险 | 发现方式 | 回退 |
| --- | --- | --- |
| 需求只是想象出来 | 记录重复频率、原流程与真实再用 | 使用现成工具，暂停独立产品 |
| 上下文压缩掉关键证据 | 对照断言、异常分支、输入与补读 | 保留原文入口，缩小压缩 |
| 状态与正文矛盾 | 程序字段校验，报告矛盾反例 | 不合规报告标记或拒绝，不改事实 |
| 规则/日志提示注入 | 越界、伪指令和可执行配置反例 | 收紧可信来源，保持只读 |
| 评测泄露答案 | 独立上下文、读取拒绝测试、白名单审查 | 重建干净评测输入，旧结果作废 |
| 自动审查永不结束 | 去重、无进展检测与预算 | 停止并报告缺口，不默认多加轮次 |
| 插件负担超过收益 | 首用/复用/维护时间与退出原因 | 保留 CLI 或短 skill |
| 垂直工具重复原项目 | 对照原工具功能与未覆盖任务 | 不重新包装，留在原工程或停止 |
