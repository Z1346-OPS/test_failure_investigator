## 0. 先处理已知阻塞

本轮未修改程序代码、未运行摄像头、未安装依赖。没有重跑完整单元测试和真实 GUI 冒烟。

通过实际调用 load_report / explain_report / Session 复现：

- 主报告 review-consistent.json，补充 review-missing-image.json：当前错误返回“范围内通过”，并称本次没有登记问题。正确要求是明确暴露新增缺图，不能判本次通过。
- 主报告添加说明后，换成其他主报告：旧说明仍保留，且未保存标志变为 False。新调查不得静默带入前一调查的说明。

- “保存说明”直接弹出文件保存对话框，没有完成报告声称的导出预览。

前两项与关闭丢失问题修复前，只做合成材料体验，不判正式验收通过。预览是否必需可以讨论，但文档与实现必须一致，用户必须能在分享前审查导出内容。

## 2. 跑一遍完整流程（约 5 分钟）

1. 选择 qr-full-ok-roi-error.json。
2. 先不展开技术详情，只读“目前发现 / 还不能确认 / 下一步”。应同时知道整图读出、选定区域出错，不能以整图读出掩盖区域错误，也不能宣称二维码内容正确。
3. 用自己的话说出“现在知道什么、还缺什么、下一步做什么”。说不出来就记录具体卡住的句子，不需要勉强理解。
4. 点“添加我的说明”，输入“验收练习：我觉得画面变好了”，再点“记录说明”。它应标为用户反馈/未独立验证，不能变成复验通过。仅在输入框打字不等于已记录。
5. 点“补充结果”，选 qr-same-image-later.json。应展示指定区域的错误在新记录中不再出现，但内容正确性仍未确认、根因仍未知。这是合成历史回放，助手没有执行解码。
6. 点“保存说明”，使用新名字，例如 trial-01.md。当前版本没有预览，保存后用文本编辑器打开审查。不要上传或发送真实材料。
7. 检查导出能否看出原始问题、补充结果、用户反馈、比较限制、下一步和证据来源；应注明未附原始文件。不要仅检查“文件存在”。

## 3. 检查关键边界（约 10 分钟）

以下每一行独立开始。结果写“通过 / 不通过 / 看不懂 / 未做”；未做不得记为通过。

| 操作 | 应看到的含义 | 不可接受的结果 |
| --- | --- | --- |
| 选择 qr-single-read.json | 单一读出，缺少独立答案 | 内容正确、正确率 100% |
| 选择 review-missing-image.json | 证据缺口，无法完成对应核对 | 直接认定磁盘写入失败 |
| 选择 review-metric-mismatch.json | 报告记录指标不一致，需要核对依据 | 直接认定摄像头损坏 |
| 选择 review-not-reviewed.json | 没有完成复核；未知计数仍未知 | 把 null 当 0，或认定复核通过 |
| 选择 task-open-failed.json | 该记录打开设备失败，原因仍待确认 | 宣称助手已检查设备或已修复 |
| 选择 review-missing-image.json，再补充 review-consistent.json | 在合成的相同对象与复核范围内，旧问题不再出现；不确认原因 | 全面恢复、硬件正常、根因确认 |
| 选择 review-consistent.json，再补充 review-missing-image.json | 新结果明确存在缺图，不能通过 | 当前已复现错误：范围内通过 |

| 对当前报告重复补充同一文件 | 没有新增独立证据 | 重复导入提高把握或增加独立验证次数 |
| 已加载正常材料后，补充 invalid-json.txt | 提示无法读取，保留已有调查内容 | 清空原内容、静默成功或崩溃 |

run_id 不同不等于现实中绝对无关；本版按此保守拒绝比较。跨运行的设备恢复，需要另外定义设备、条件、时间和检查范围的关联证据，目前不能把这项能力算作已完成。

## 4. 保存、取消与换报告（约 5 分钟）

只用虚构说明操作：

1. 正常保存后打开文件，逐项对照界面。用户说明、关键错误和未知状态都应保留。
2. 再保存到同名文件，应拒绝覆盖；原文件内容应不变。
3. 直接点“保存说明”后取消，应留在原界面，不显示保存成功。
4. 添加新说明后关闭窗口，在未保存提示中选“返回”，应保留内容。
5. 再关闭，在未保存提示中选“保存说明”，然后取消文件选择。应保持原窗口与未保存状态；当前代码有继续关闭的风险。
6. 添加“只属于第一份报告的说明”，保存，然后“选择报告”打开另一种材料。旧说明不得默默混入新调查；当前逻辑已复现混入问题。

如遇丢内容、串入说明、结论矛盾，记录一次就够，交回修复，不必反复尝试或拿真实记录试错。

## 6. 判断是否简洁好用

在平常使用的 Windows 缩放比例下检查：文字是否清晰、按钮是否被挡、缩小窗口后能否滚动到底部、技术详情能否展开并折回、系统选文件与保存对话框是否能独立完成操作。记录实际分辨率和缩放；未测试其他缩放就写未测试，不必为这轮改变系统设置。

首次阅读主区后，尝试在一分钟内回答三个问题：发生了什么？还不能确认什么？我下一步具体做什么？一分钟只是观察目标，不是已经证明的产品指标。需要别人解释的词和点击失败的地方，都是产品要改进的证据。

作者自测通过后，再找一位未参与设计的 Windows 用户试一个合成案例。先让对方自己操作；卡住时可以帮助，但记录帮助发生在哪里。不要把熟悉系统的作者自测写成独立用户试用，也不要把单次试用写成普遍效果证明。

## 7. 留下最小记录并作决定

每项用下面一行即可，不需要写长报告：

`文件 / 操作 / 实际显示或卡住位置 / 预期 / 通过、不通过、看不懂或未做`
